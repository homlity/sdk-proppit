Para qué sirve

Un puente entre tu inventario y Proppit

Proppit (LIFULL Connect) es el portal donde las inmobiliarias publican su inventario. Su Real-Time API v2 permite enviar anuncios por API en lugar de cargarlos a mano desde el panel web. Este SDK es la capa PHP que Homlity —y cualquier CRM, lonja o portal integrado con Homlity— usa para hablar con esa API.

Qué te ahorra

Token que expira

Pide el token, lo cachea en memoria y lo renueva 30 s antes de vencer. Tú nunca lo tocas.

Payloads rechazados

Valida enums de moneda, locale, áreas, coordenadas y estrato antes de gastar una llamada HTTP.

Errores crudos

Convierte cada status en una excepción tipada que puedes capturar por caso de negocio.

Caídas y 429

Reintenta 5xx y rate limits con backoff exponencial y jitter, respetando Retry-After.

Publisher no habilitado

Modela el estado real de activación y distingue el 403 de Proppit de un problema de credenciales.

Secretos en logs

Redacta tokens, secrets, emails y teléfonos de forma recursiva en todo lo que se loguea.

Qué no hace, por diseño

  • No gestiona colas ni jobs. Eso lo pone tu aplicación (ShouldQueue, Horizon).
  • No persiste nada. Tú decides qué guardar: referenceId, estado del publisher, timestamps.
  • No sube imágenes. Envías URLs públicas y el ingester de Proppit las descarga.
  • No implementa GET /property-types todavía — el catálogo de tipos, amenities y reglas por país.
Cómo está hecho

Arquitectura en 30 segundos

Cinco capas, cada una detrás de una interfaz en src/Contracts/. Cualquier pieza es reemplazable desde el contenedor de Laravel.

Los tres identificadores que debes entender

La confusión más cara de esta integración es mezclar las credenciales del sistema con la identidad de cada inmobiliaria. No son lo mismo.

Regla de oro: client_id y client_secret identifican a tu sistema ante Proppit — se entregan una sola vez y viven solo en el .env. Cada inmobiliaria se identifica con un publisher.externalId que tú generas y mantienes.

Automático

Autenticación

No tienes que hacer nada. Así funciona por dentro:

  1. ClientCredentialsAuthenticator llama POST {base_url}/token con {"user": CLIENT_ID, "password": CLIENT_SECRET}.
  2. Proppit responde {"token": "…", "expiration": <unix_ts>}.
  3. El token se guarda en memoria en la instancia y se reutiliza.
  4. Se renueva cuando faltan menos de 30 segundos para expirar.
  5. Cada request lleva Authorization: Bearer <token>.
Respuesta de /tokenResultado
401 · 403AuthException — "Proppit rejected the client credentials"
2xx sin token o expirationAuthException — respuesta inválida
Error de redAuthException con la excepción de Guzzle como previous

Rendimiento: el token se cachea por instancia y en Laravel ProppitClient es un singleton, así que dentro de un mismo request o job solo se pide un token. Si ejecutas muchos procesos cortos (un comando por inmueble), implementa un ProppitAuthenticatorInterface que cachee el token en Redis y evita pedir uno por proceso.

Paso 3

Quick start

Con Laravel

php
use Proppit\ProppitClient;

$client = app(ProppitClient::class);   // singleton, ya cableado

$client->properties();   // PropertyApiInterface
$client->publishers();   // PublisherApiInterface

O inyectado por constructor, que es lo habitual en un job:

php
final class SincronizarInmuebleJob implements ShouldQueue
{
    public function __construct(private readonly int $inmuebleId) {}

    public function handle(ProppitClient $proppit): void
    {
        $proppit->properties()->publish($this->payload());
    }
}

Standalone, sin Laravel

php
use GuzzleHttp\Client;
use Proppit\Api\{PropertyApi, PublisherApi};
use Proppit\Auth\ClientCredentialsAuthenticator;
use Proppit\Config\ProppitConfig;
use Proppit\Http\GuzzleProppitHttpClient;
use Proppit\Normalizers\{PropertyPayloadNormalizer, PublisherPayloadNormalizer};
use Proppit\ProppitClient;
use Proppit\Support\StructuredLogger;

$config = ProppitConfig::fromArray([
    'base_url'      => 'https://real-time.proppit.com/api/v2',
    'client_id'     => getenv('PROPPIT_CLIENT_ID'),
    'client_secret' => getenv('PROPPIT_CLIENT_SECRET'),
    'country'       => 'CO',
]);

$guzzle = new Client();
$auth   = new ClientCredentialsAuthenticator($config, $guzzle);
$logger = new StructuredLogger(enabled: true, logger: $miLoggerPsr3);
$http   = new GuzzleProppitHttpClient($guzzle, $config, $auth, $logger);

$client = new ProppitClient(
    properties: new PropertyApi($http, new PropertyPayloadNormalizer(), $config),
    publishers: new PublisherApi($http, new PublisherPayloadNormalizer(), $config),
);

El repositorio incluye ejemplos ejecutables en examples/: sync_publisher.php, publish_property.php, update_property.php y find_property.php.

El orden importa

Flujo de integración de una inmobiliaria

Estos pasos son una secuencia real: saltarse el tercero hace que el sexto falle con un 403 que ningún cambio de código resuelve.

  1. Configurar credenciales del sistema

    Una sola vez para toda la instalación: PROPPIT_CLIENT_ID, PROPPIT_CLIENT_SECRET y PROPPIT_COUNTRY en el .env.

  2. Registrar la inmobiliaria como publisher

    createOrUpdate() con un externalId estable. Guarda proppit_publisher_id y proppit_external_id en tu base de datos.

  3. Solicitar la activación a Proppit

    Paso manual. Proppit debe habilitar el publisher; el SDK no puede hacerlo por ti. Usa la plantilla de la sección de publishers.

  4. Confirmar que quedó activo

    Verifica con status($externalId) que canPublish() === true, o espera confirmación explícita del equipo de Proppit. Marca proppit_can_publish = true.

  5. Depurar el inventario previo de la cuenta

    Proppit recomienda eliminar las propiedades cargadas a mano antes del primer sync por API. Si no lo haces, arriesgas duplicados y PUT que sobrescriben el inmueble equivocado.

  6. Publicar por API y guardar el referenceId

    Solo si proppit_can_publish === true. Persiste el referenceId de cada inmueble: es la única llave para actualizar o eliminar después.

  7. Mantener los cambios por API, no por el panel web

    Todo cambio posterior va por update(). Editar desde el panel de Proppit rompe la consistencia con tu base de datos.

Inmobiliarias

Publishers

Publisher enviado ≠ publisher activo. Crear un publisher en Proppit no lo habilita para publicar. Proppit debe activarlo manualmente. Hasta entonces, cada intento de publicar responde {"status": 403, "error": "Publisher could not publish"}. Esto no es un problema de credenciales.

Registrar o actualizar

php
use Proppit\DTO\PublisherPayload;

$externalId = 'homlity_agency_' . $inmobiliaria->uuid;

$response = $client->publishers()->createOrUpdate(new PublisherPayload(
    externalId: $externalId,              // → campo `id` en la API de Proppit
    name:       $inmobiliaria->nombre,
    email:      $inmobiliaria->email_contacto,
    phone:      $inmobiliaria->telefono,  // opcional
));

$inmobiliaria->update([
    'proppit_external_id'      => $externalId,
    'proppit_publisher_id'     => $response->publisherId(),
    'proppit_publisher_status' => $response->activationStatus,  // 'pending_activation'
    'proppit_can_publish'      => $response->canPublish(),      // false por defecto
    'proppit_last_request_id'  => $response->requestId,
    'proppit_last_synced_at'   => now(),
]);

createOrUpdate() hace un find() interno y decide entre POST (crear) y PUT (actualizar). Es idempotente.

Reglas del externalId

  • Único y estable por inmobiliaria — cambiarlo desconecta un publisher ya activado.
  • Solo letras, dígitos, -, _, . y @; máximo 255 caracteres. El SDK lo valida.
  • No uses el email, nombre comercial ni NIT como valor principal: usa el UUID o ID interno.
  • Formato recomendado: homlity_agency_{uuid}.

Estados de activación

EstadoSignificado¿Puede publicar?
pending_syncTodavía no enviado a Proppitno
syncedEnviado; Proppit no confirmó activaciónno

Proppit todavía no estandariza el campo de activación, así que PublisherResponse::fromArray() inspecciona canPublish, can_publish, state, activationStatus, active y status — y solo marca active si Proppit lo confirma explícitamente. Ante la duda, asume pending_activation.

Consultar el estado

php
$response = $client->publishers()->status($externalId);  // lanza ApiException(404) si no existe

if ($response->canPublish()) {
    $inmobiliaria->update([
        'proppit_publisher_status' => $response->activationStatus,  // 'active'
        'proppit_can_publish'      => true,
        'proppit_activated_at'     => now(),
    ]);
}

// find() devuelve null en 404 en vez de lanzar; status() lanza. Elige según el caso.
$response->isPendingActivation();  // true si 'pending_activation' o 'synced'
$response->raw;                    // respuesta cruda completa para inspección

El referenceId es tuyo. Guárdalo en tu base de datos: es la única forma de actualizar o borrar el anuncio después. Convención sugerida: CO-{inmueble_id}.

Actualizar, consultar, eliminar

php
// PUT es un reemplazo COMPLETO: reenvía todos los campos requeridos.
$response = $client->properties()->update('CO-1001', $payload);

// Mono-inmobiliaria: usa PROPPIT_PUBLISHER_EXTERNAL_ID de la config
$response = $client->properties()->find('CO-1001');

// Multi-inmobiliaria: pasa el externalId de la agencia. Devuelve null si viene vacío.
$response = $client->properties()->findByExternalId(
    $inmobiliaria->proppit_external_id,
    'CO-1001',
);

$response = $client->properties()->delete('CO-1001');
echo $response->status;  // deleted

find() y delete() lanzan ValidationException si no hay publisher_external_id configurado. En instalaciones multi-inmobiliaria, usa siempre findByExternalId().

Qué valida el normalizador antes de salir a la red

  • Presencia de los seis campos requeridos y referenceId no vacío.
  • publisher.externalId presente y no vacío.
  • property.type, property.location y coordenadas numéricas.
  • operations no vacío; type, price.value numérico y currency en el enum.
  • title y description con locale válido y text no vacío.
  • Cada multimedia.pictures[].url como URL válida.
  • Áreas con value numérico y unit igual a sqm.
  • stratum entre 1 y 7; condition, furnished y visibility contra sus enums.
  • Limpieza recursiva de null y strings vacíos antes de serializar.

Cualquier fallo lanza ValidationException sin consumir una llamada HTTP.

Producción

Manejo de errores

php
use Proppit\Exceptions\{ApiException, AuthException, ForbiddenException,
    PublisherPermissionException, RateLimitException, ValidationException};

try {
    $response = $client->properties()->publish($payload);

} catch (PublisherPermissionException $e) {
    // 403 "Publisher could not publish" — el publisher NO está activado.
    // No son credenciales incorrectas. Ningún cambio de código lo resuelve.
    $e->requestId();        // Request ID de Proppit, para soporte
    $e->originalError();    // "Publisher could not publish"
    $e->rawResponse();      // JSON saneado del cuerpo del 403
    $e->operationalHint();  // guía legible para operadores

} catch (ForbiddenException $e) {
    // 403 genérico, no relacionado con la activación del publisher.

} catch (ValidationException $e) {
    // El payload no pasó la validación local — no hubo llamada HTTP.

} catch (AuthException $e) {
    // 401 o credenciales rechazadas por el endpoint /token.

} catch (RateLimitException $e) {
    $e->retryAfter;         // segundos, si Proppit envió Retry-After

} catch (ApiException $e) {
    // Cualquier otro error HTTP (400, 404, 5xx) o error de transporte.
    $e->statusCode; $e->method; $e->endpoint; $e->proppitErrorCode; $e->context();
}

El orden de los catch importa. Van de más específico a más general: si pones ApiException primero, nunca alcanzarás PublisherPermissionException.

        'proppit_can_publish'      => false,
        'proppit_last_error'       => $e->getMessage(),
        'proppit_last_request_id'  => $e->requestId(),
    ]);

    Log::warning('proppit_publisher_no_activado', [
        'external_id' => $e->publisherExternalId,
        'request_id'  => $e->proppitRequestId,
    ]);
}

PropertyApi reinyecta el publisher.externalId del payload en la excepción, así que $e->publisherExternalId te dice qué inmobiliaria está bloqueada.

Producción

Reintentos y límites

CondiciónComportamiento
429 Too Many RequestsUsa Retry-After si viene; si no, backoff exponencial con jitter
5xxBackoff exponencial con jitter
4xx salvo 429No reintenta — son errores del cliente
Error de transporteNo reintenta — ApiException con statusCode = 0

Fórmula del backoff: retry_delay_ms × 2^(intento-1) + jitter(0–100 ms). Con los valores por defecto el peor caso son 4 intentos y ≈ 3,5 s de espera acumulada, más 4 × timeout en el peor escenario de red. Dimensiona el timeout de tu job en consecuencia.

Proppit no documenta sus rate limits. El SDK maneja el 429 de forma defensiva, pero no paralelices agresivamente: publica desde una cola, un job por inmueble.

php
public function handle(ProppitClient $proppit): void
{
    try {
        $proppit->properties()->publish($this->payload());
    } catch (RateLimitException $e) {
        $this->release($e->retryAfter ?? 60);
    } catch (PublisherNotReadyException $e) {
        $this->fail($e);   // no reintentar: requiere acción manual de Proppit
    }
}

Redacción automática

Redactados por completo (***):

authorizationclient_secretapi_secretapi_passwordpasswordtokenaccess_tokenrefresh_tokenbearersignaturesecretemailphonewhatsapp

Redactados parcialmente (4 primeros caracteres + ***):

client_idapi_keyapi_user

La redacción es recursiva y también se aplica al context() de las excepciones y a PublisherPermissionException::rawResponse(). Puedes reutilizarla:

php
StructuredLogger::sanitize($arrayConDatosSensibles);

email y phone se redactan también en payloads salientes. Es deliberado — son PII. No te alarmes si no ves el contacto en los logs.

Mapper propio, conservando la validación oficial

php
final class InmuebleMapper implements PropertyPayloadMapperInterface
{
    public function __construct(private readonly PropertyPayloadNormalizer $base) {}

    public function normalize(PropertyPayload|array $payload): array
    {
        $payload = $this->aplicarReglasDeNegocio($payload);

        return $this->base->normalize($payload);  // conserva la validación del SDK
    }
}
Token en Redis

Implementa ProppitAuthenticatorInterface si corres muchos procesos cortos y no quieres un /token por proceso.

Cliente HTTP propio

Implementa ProppitHttpClientInterface para instrumentar con OpenTelemetry, un circuit breaker o una caché de respuestas.

Headers extra

Más simple que un cliente propio: 'custom_headers' => ['X-Homlity-Trace' => $traceId] en la config.

Mockear el SDK en tu aplicación

Sustituye el cliente HTTP y no saldrá ni un byte a la red:

php
use Proppit\Contracts\ProppitHttpClientInterface;
use Proppit\DTO\HttpResponse;

$mock = $this->createMock(ProppitHttpClientInterface::class);
$mock->method('request')->willReturn(
    new HttpResponse(201, [], '{}', ['referenceId' => 'CO-1', 'status' => 'published'])
);

$this->app->bind(ProppitHttpClientInterface::class, fn () => $mock);

Para ejercitar la ruta del publisher no activado:

php
$mock->method('request')->willThrowException(
    new PublisherNotReadyException('homlity_agency_1', 'req-123', [])
);

O mockea la API completa cuando solo te interesa tu lógica de negocio:

php
$api = $this->createMock(PropertyApiInterface::class);
$api->expects($this->once())->method('publish');
$this->app->bind(PropertyApiInterface::class, fn () => $api);

Si quieres ejercitar el SDK completo —retries, mapeo de errores— usa GuzzleHttp\Handler\MockHandler contra respuestas fabricadas.
